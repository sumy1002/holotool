# HoloTool — Hololive Dreams「High & Low」自動遊玩工具

這是一個針對《ホロライブドリームス》(Hololive Dreams) 裡的小遊戲
**High & Low（カードオブグリード）** 設計的螢幕監測自動化工具。

流程對應遊戲玩法：

1. **門票關卡**：發 5 張牌，選擇保留/更換，換牌後至少要湊到「兩對」才能拿到門票，
   進入比大小環節（未達標則這次下注失敗）。
2. **比大小關卡**：亮出一張牌，猜下一張會「比較大」還是「比較小」，猜對就加倍，
   可以選擇繼續加倍或收手兌現。
3. **每日上限**：金額翻倍超過上限（約 12800 硬幣）時，遊戲會強制結束該輪並顯示
   「已達最高獲得金額，遊戲結束」。這個上限**每天可以達成兩次**：
   - 第 1 次：畫面停在結算頁，按「再玩一次」還能玩第二輪
   - 第 2 次：遊戲直接關掉牌桌，今天就到此為止

工具會：按下 **F9** 後開始自動判斷、自動玩，並持續記錄「今天看過的牌」來估計機率，
用來決定選牌/比大小的最佳策略；偵測到被踢出牌桌畫面（=可能已達每日上限）時自動停止。

> ⚠️ **使用須知**：對遊戲畫面進行自動化操作，可能違反遊戲的服務條款，有帳號被
> 處分的風險，請自行評估後使用，本工具僅供個人研究/省力用途。另外因為我沒有你
> 實際的遊戲畫面，下面列出的「假設」很可能需要你依實際狀況調整（見下方「已知假設」）。

```

    src/                   #   主要程式邏輯

      build_installer.py   #     一鍵產生給別人的 app/dist/HoloToolSetup.exe

      ref/                 #     校準用的範例畫面（六張 jpg，框選時顯示在角落）
```

幾個重點：

* **`gui.py` 不吃資料夾名字。** 它會自己找「裡面有 `src\paths.py` 的那個子資料夾」，
  所以你想把 `app\` 改成別的名字也不會壞。
* 所有指令都在**專案根目錄**下，以 `app\` 開頭，例如
  `app\.venv\Scripts\python.exe app\tools\check_setup.py`。
* 打包成 exe 之後結構會變平（`HoloTool.exe` 旁邊直接是 `config\`、`card_templates\`），
  這是刻意的 —— 拿到安裝檔的人不需要看到原始碼的分層。

## 安裝

已內建一個虛擬環境 `app\.venv`，若要重新安裝：

```powershell
cd F:\holotool
python -m venv app\.venv
app\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

> 舊版的 `.venv` 在最外層。跑過 `app\packaging\tidy_project.py` 之後它會被搬進
> `app\`；如果搬不動（你正在用它跑腳本，Windows 會鎖住），腳本會產生一個
> `move_venv.bat`，關掉終端機再雙擊它就好。

> ⚠️ **虛擬環境搬過位置之後，`Scripts\` 底下那些 `.exe` 會壞掉。**
> `pip.exe`、`pyinstaller.exe` 這些其實是很小的啟動器程式，**把建立當下的
> `python.exe` 絕對路徑寫死在檔頭**。整個 `.venv` 一搬家，它們就會去找一個
> 已經不存在的路徑，執行起來只丟一個結束碼 1 —— 看起來像 PyInstaller 壞了，
> 其實是啟動器壞了。
>
> `python.exe` 本身不受影響（靠旁邊的 `pyvenv.cfg` 定位），所以：
>
> * **平常一律用 `python.exe -m 模組名`**，例如 `python.exe -m pip install ...`。
>   打包腳本現在也都改成這樣，不會再踩到。
> * 想把那些 `.exe` 修回來（這樣才能直接敲 `pip install`）就跑一次：
>   `app\.venv\Scripts\python.exe app\packaging\repair_venv.py`

> `keyboard` 套件在 Windows 上要監聽全域熱鍵，某些情況下需要「以系統管理員身分」
> 執行終端機才能正常運作，若按 F9 沒反應，請改用系統管理員權限重開終端機再試。

## 快速開始（推薦：直接雙擊 exe）

打包完成後，雙擊下面任一處即可開啟，不必再打指令：

- `app\dist\HoloTool\HoloTool.exe`
- 桌面上的 `HoloTool` 捷徑

若還沒打包，或想重新產生 exe：

```powershell
cd F:\holotool
app\.venv\Scripts\python.exe app\packaging\build_exe.py
```

設定檔、卡牌樣板、統計都會存在 **exe 同一個資料夾**（`app\dist\HoloTool\`），不要只複製 exe 單檔到別的地方。

開發時也可以直接跑原始碼：

```powershell
cd F:\holotool
app\.venv\Scripts\python.exe gui.py
```

介面分成四個分頁，照順序用就對了：

| 分頁 | 做什麼 |
|---|---|
| **主控台** | 從下拉選單挑遊戲視窗 → 按「使用此視窗」（**視窗比例會自動偵測並套用對應的校準**）；之後用「啟動/停止」控制自動遊玩，看即時 log 與今日統計，按「補算未記錄的數值」餵機率模型 |
| **校準** | 已內建從截圖量好的預設框選。可直接用，或按「套用截圖預設框選」還原；對不準再逐項微調。框選時角落會有**範例圖**、遊戲畫面上會有**建議框** |
| **點數/花色樣板** | 在選牌畫面按「讀取目前畫面」→ 程式自動切出五張牌的左上角並猜出牌面 → 確認/修正代號 → 按「全部儲存」。代號欄只吃英數字、大小寫沒差、**關掉了輸入法**；「蒐集進度」收在下方可展開 |
| **設定** | 分成「比對門檻設定」（預設展開）、「動作時間設定」（預設收合）與其餘策略參數 |

第一次使用可以先勾「除錯模式」並打開「顯示即時辨識結果」，確認畫面狀態與手牌辨識
沒問題後再取消勾選、正式點擊。注意：每次按「啟動」都會依**當下**的勾選狀態套用，
取消勾選後若沒重新啟動，不會自動變成會點擊。

啟動後遊戲視窗要保持在最前面。熱鍵 **F9** 啟動/停止、**F10** 緊急停止在 GUI 中同樣有效。

### 只有一個螢幕：用迷你懸浮視窗

主控台右邊有一顆 **「⤡ 縮成迷你視窗」**。按下去主視窗會收起來，只留一個
釘在最上層的小方塊：一顆狀態燈（綠＝執行中）、一顆啟動／停止、一顆 **▣** 還原主視窗。

- 預設出現在螢幕右下角、工作列上方一點；**拖那顆圓點**可以移動，放手時位置會記進
  `config.json` 的 `mini_panel`，下次打開還在同一個地方。
- 顯示前一定會把座標夾回螢幕範圍內。換螢幕或改解析度之後，舊座標很可能落在畫面外，
  而這個視窗沒有標題列也不出現在工作列 —— 跑出去就真的找不回來了。
- 萬一迷你視窗在某台電腦上顯示不出來，程式會**維持主視窗開啟**並提示你改用 F9／F10，
  不會讓你兩個視窗都沒有。

### 視窗長寬比：一組校準，自動換算到所有比例

**遊戲不是依視窗重排 UI。** 它把一個固定 **16:9 的內容框置中**放進視窗，所有 UI 都排在
那個框裡；只有**背景圖**拉滿整個視窗。因為背景填滿了，看起來沒有黑邊，才會像是重排。

證據（2026-08-21 量三種比例的實機截圖，換算到內容框座標後）：

| 五格手牌 | 16:9 (1474×829) | 4:3 (1269×952) | 差 |
|---|---|---|---|
| 牌0 | 0.0725 0.3112 0.1479 0.3703 | 0.0725 0.3109 0.1481 0.3712 | 0.0009 |
| 牌4 | 0.7809 0.3112 0.1479 0.3703 | 0.7809 0.3109 0.1481 0.3712 | 0.0009 |

一致到 1 個像素。所以**一組校準就能精確算出其他比例**，換算誤差 1~4 像素。
內建已經有 21:9、16:9、4:3 三組；換到沒見過的比例時程式會自動算一組出來，log 會說明。

唯一的例外是**對話框最下面那排動作按鈕**（取消／進行挑戰／再一次）—— 它們釘在
**視窗底部**，不在內容框裡。用同一組轉換去預測，差別非常明確：

| 地標 | 內容框預測誤差 | 貼視窗底預測誤差 |
|---|---|---|
| 卡片上下緣 | 0.0 px | 118.1 px |
| 大／小膠囊中心 | 0.3 px | 118.4 px |
| 取消 上緣 | 118.4 px | **0.3 px** |
| 進行挑戰 中心 | 111.0 px | **7.1 px** |

樣板縮放倍率也只跟內容框高度有關，跟視窗寬度無關 —— 舊公式用視窗寬度比，在 16:9
與 4:3 都**差 24%**（只有在接近 21:9 時剛好差不多，所以一直沒被發現）。這就是換比例
之後畫面標記分數整排掉下來的原因。

#### 比例是自動偵測的，不用自己去挑

比例的偵測與切換都在**主控台**的「遊戲視窗」區塊（以前放在「校準」分頁）：

- 按「使用此視窗」的那一刻就抓比例、套上對應的那一組校準；沒有那一組就從最接近的
  **精確換算**一組出來。
- 之後每兩秒檢查一次視窗尺寸，**把遊戲從 21:9 拉成 16:9 也會自動跟著換**，
  不需要自己想起來要按什麼按鈕。
- 想固定用某一組，就把「視窗比例」下拉選單從「自動偵測」改成那一組 ——
  自動偵測會關掉，直到你把它改回「自動偵測」。這個選擇存在 `config.json` 的
  `auto_detect_profile`。

「校準」分頁只剩最上面一行告訴你**現在校準的是哪一組**，因為那是校準時唯一需要
知道的事（框完的結果只會寫進那一組）。

想手動覆蓋某個比例的校準：

1. 把遊戲視窗調成那個比例（主控台會顯示偵測到的比例）
2. 按主控台的 **「另存為目前比例的校準」**
3. 重新框選 —— 框完的結果**只會存進這一組**，其他比例完全不受影響

### 校準時看得到「這一項要框到哪」

文字說明「框選左上角 High & Low 標題」有太多解讀空間：含不含外框？框大一點是不是
比較保險？猜錯的下場是辨識分數莫名偏低，而且**完全看不出原因**。所以框選遮罩上
同時給兩種視覺提示：

1. **範例圖**（螢幕角落，半透明）—— 六張實機畫面的乾淨縮圖，這一項的預設框畫在
   上面、框外壓暗，所以「要框的範圍」是圖上唯一亮的地方。按 **H** 可以隱藏／顯示；
   範例圖預設在右上角，如果這一項本身就在右上角（例如「大」按鈕），它會自動換到
   別的角落，不會擋住你要瞄的地方。
2. **建議框／建議十字**（直接畫在遊戲畫面上）—— 黃色虛線框（含四角實線角標）是
   建議範圍，青色虛線十字是建議點擊位置。照著描即可，覺得不準就自己重框。
   已經校準過的項目會畫**你自己上次的框**，沒校準過的畫內建預設。
   遮罩上還有一圈細虛線標出遊戲視窗的用戶端範圍，避免框到視窗外面。

範例圖存在 `app\defaults\ref\*.jpg`（六張，各約 30 KB），由
`app\tools\make_ref_images.py` 從 `debug_captures\` 的實機截圖產生 ——
那些截圖上都被除錯腳本畫過彩色框線，腳本會把框線抹掉再縮圖。
對應關係寫在 `app\src\calibguide.py`，`app\tests\test_calib_guide.py`
會守著「每個校準項目都有對應的範例畫面、檔案真的都在」。

唯一沒有範例圖的是**「已達最高獲得金額」**那兩項（標記與「再玩一次」）——
那個畫面從頭到尾只出現在對話紀錄裡，拿不到像素。它們只會有建議框。

### 畫面標記樣板：只有七個，而且一組就夠

校準項目很多，但**只有七項會真的存成圖片**，其餘全部只存座標：

| 會存 PNG（判斷「現在是哪個畫面」） | 檔名 |
|---|---|
| 牌桌 logo | `table_marker.png` |
| 選牌畫面提示 | `ui_draw_prompt.png` |
| 過關 | `ui_congrats.png` |
| 翻倍機會 | `ui_challenge.png` |
| 失敗 | `ui_fail.png` |
| 「要再玩一次撲克嗎？」 | `ui_poker_fail.png` |
| 已達最高獲得金額 | `ui_max_win.png` |

其他項目（五格手牌、比大小的牌、以及所有點擊點）存的是 0～1 的比例值，
換算靠 `content_box()` / `retarget()`，不需要圖。

**不需要為每個長寬比各準備一組。** 遊戲是把一個固定的 16:9 內容框置中，
只有背景在拉伸，標記都長在內容框裡面，所以不同長寬比之下標記只是單純縮放。
倍率由 `expected_marker_scale()` 用**內容框高度的比值**算出來：

```python
return content_height(client_width, client_height) / ref_box
```

（這個公式本來是用視窗寬度的比值，在接近 21:9 時剛好差不多，一換成 16:9
就用錯 24% 的倍率，所有標記分數整排掉下來。已修。）

### 內建標記樣板的解析度：越大越好

比對前的縮放**縮小很安全、放大會糊**。內建那批是從 1024 寬的縮圖裁出來的，
而大部分人的視窗都比 1024 寬 —— 等於一直在放大。實測 1365 寬的視窗下
選牌 37% / 過關 21% / 翻倍 23%，門檻 0.80 一個都過不了，
而使用者完全看不出原因（分數低，但畫面明明就在那裡）。

所以有兩個獨立的常數，**不要混用**：

| 常數 | 意思 | 什麼時候該動 |
|---|---|---|
| `SCREENSHOT_CLIENT_WIDTH/HEIGHT` | 內建**校準座標**是在多大的視窗量的（座標是比例，這只是換算基準） | 重新量一整套預設座標時 |
| `BUNDLED_MARKER_WIDTH/HEIGHT` | 內建**標記圖**是在多大的視窗裁的 | 換掉 `defaults/ui/*.png` 時 |

`config.json` 的 `templates.capture_client_width` 預設就是取後者，
`expected_marker_scale()` 讀不到欄位時的退回值也是後者 ——
寫死 1024 的話，升級了內建圖、舊 config 卻會用錯倍率。

#### 怎麼換成原生解析度的標記

1. 主控台 →「**存一張目前畫面（PNG）**」。這顆會直接抓遊戲視窗的**用戶端區域**
   存到 `debug_captures\shot_<寬>x<高>_<時間>.png`。
   **不要**自己用截圖工具裁 —— 很容易連視窗邊框／標題列一起裁進去，或被系統
   顯示縮放動過，尺寸一旦不對，裁出來的樣板就沒有意義。
   每個標記只出現在自己的畫面上，所以一個畫面存一張。
2. 用校準座標把標記裁出來：

```powershell
app\.venv\Scripts\python.exe app\tools\promote_ui_templates.py --dry-run ^
    --shot table_marker=debug_captures\shot_1365x576_a.png

app\.venv\Scripts\python.exe app\tools\promote_ui_templates.py --promote ^
    --shot table_marker=...png --shot congrats_marker=...png
```

不加 `--promote` 只會更新你自己的 `card_templates\`；加了才會一起升級
`defaults\ui\`（給別人開箱用的那份）並自動改寫 `BUNDLED_MARKER_WIDTH/HEIGHT`。
所有截圖必須是同一個視窗大小 —— 內建樣板只能記錄一個來源解析度，
混著用會讓倍率算錯，工具會直接拒絕。覆蓋前一律先留 `.bak`。

#### 2026-08-21：內建標記換成 1365×576 原生截圖的實測

用 27 個實機畫面量的（1365 原生 21 張 + 舊的 1024 截圖 6 張），
`marker_pads` / `marker_thresholds` 都用設定檔裡的真實值：

| 標記 | 舊圖(放大 1.32 倍) | 新圖(原生) |
|---|---|---|
| 牌桌 logo | 命中 11/11，但**誤判上限 0.82 = 門檻 0.82** | 11/11，誤判上限降到 0.73 |
| 選牌提示 | 1/2 | 1/2 → 調門檻後 2/2 |
| 過關 | 1/1 | 1/1 |
| 翻倍機會 | 7/7（0.95） | 7/7（1.00） |
| 失敗 | **0/2 —— 完全抓不到**（0.72 對門檻 0.82） | **2/2**（0.94） |
| 要再玩一次撲克嗎 | 3/3 | 3/3 |

兩個重點：

* **失敗標記在實機上本來根本沒生效**（0.72 < 0.82）。這不是門檻調太高，
  是樣板放大 1.32 倍之後糊掉。
* 牌桌 logo 舊圖的誤判上限剛好等於門檻，等於隨時可能在非牌桌畫面誤判
  「還在牌桌」。新圖有 0.23 的餘裕。

同時重新量了兩個門檻（`config_version` 6 會強制套用，見下）：

| 標記 | 正例最低 | 反例最高 | 舊門檻 | 新門檻 |
|---|---|---|---|---|
| `draw_prompt` | 0.70 | 0.64 | 0.78 ✗ | **0.67** |
| `fail_marker` | 0.81 | 0.77 | 0.82 ✗ | **0.79** |

這兩個框裡都有「會變的東西」：選牌提示是淡入淡出的，框內還含大片背景漸層；
失敗那格的大標題本身會變（失敗／無對子／一對…）。所以餘裕天生就小，
跟解析度無關。判斷「這一局結束了」請以 `poker_fail_marker` 為主（餘裕 0.45）。

> `config_version` 6 做兩件事：把 `marker_thresholds` 換成新預設；以及
> **在「你還在用內建樣板」的前提下**把 `capture_client_width/height` 同步成
> 1365×576。判斷方式是比對 `card_templates\` 那六張與 `defaults\ui\` 的
> **檔案內容**（不是檔名）—— 只要有一張是你自己抓的，整組都不動，
> 因為那個數字是你自己的截圖解析度，蓋掉會讓你所有樣板都縮放錯。

### 「設定」分頁分成三區

二十幾個欄位平鋪成一長串，要調「遊戲漏收點擊」的那幾個秒數得先在門檻、策略、
雜項之間找。現在分成：

| 區塊 | 什麼時候調 | 預設 |
|---|---|---|
| **比對門檻設定** | 認不到牌、認不到畫面標記 | **展開**（最常動的一區） |
| **動作時間設定** | 遊戲跑得慢、常常漏收點擊 | **收合**（調過一次通常就不用再動，而且它九個欄位，一直攤開會把下面的東西擠出視窗外） |
| 其餘 | 策略與雜項（模擬次數、續押勝率、每日上限次數…） | 直接攤在外面 |

點標題那一列（`▼ 比對門檻設定`）就能收合／展開。

分組資料放在 `app\src\settings_layout.py` 而不是 `gui.py` —— 那邊沒有 tkinter
依賴，所以測得到「每個欄位都被歸到某一組、沒有重複、路徑在 `DEFAULT_CONFIG` 裡
真的存在」。分組之後多了一種很難發現的壞法：欄位排在畫面上但沒進到存檔清單裡，
使用者調了值、按了儲存、程式回報「設定已儲存」，那一格卻被忽略。
`app\tests\test_settings_layout.py` 就是在守這個。

## 做一個給別人用的安裝程式

要把整套工具交給沒有 Python 的人，就打包成單一安裝檔。對方雙擊、選資料夾、按
Install 就好，**不需要裝 Python，也不需要裝任何其他東西**（Python 直譯器、OpenCV
這些都已經包在裡面）。

### 你這台打包機要準備的（只做一次）

1. **Inno Setup 6**（免費，約 5MB）：<https://jrsoftware.org/isdl.php>
   下載 `innosetup-6.x.x.exe`，一路 Next 裝完即可。
   *想要中文安裝畫面的話*，另外到 <https://jrsoftware.org/files/istrans/> 抓
   `ChineseTraditional.isl`，丟進 Inno Setup 的 `Languages` 資料夾；沒有的話
   安裝畫面會是英文（只有 Next / Install / Finish 幾顆按鈕）。
2. **圖示**：把要當圖示的圖片存成 `icon.png` 放在專案根目錄。
   打包時會自動用 `make_icon.py` 轉成多尺寸的 `icon.ico`，exe 與安裝檔都會套用。

### 打包

```powershell
cd F:\holotool
app\.venv\Scripts\python.exe app\packaging\build_installer.py
```

它會依序做：產生圖示 → PyInstaller 打包 → Inno Setup 壓成安裝檔，最後產出

```
app\dist\HoloToolSetup.exe      ← 要拿給別人的就是這一個
```

常用參數：

| 參數 | 用途 |
|---|---|
| `--skip-build` | 跳過 PyInstaller（剛打包過、只想重做安裝檔時用，快很多） |
| `--version 1.2.0` | 指定版本號（顯示在控制台的「安裝的應用程式」裡） |

### 安裝程式的行為

- **預設裝到 `%LOCALAPPDATA%\HoloTool`**，安裝畫面可以自己改路徑。
  不預設 `C:\Program Files` 是有原因的：這個程式會把校準檔、樣板、log 寫在
  **自己旁邊**，裝在唯讀的位置一開啟就會出錯。安裝程式會在按下 Install 之前
  實際試寫一個檔，選到沒權限的資料夾會直接擋下來並提示。
- 自動建立開始選單捷徑；桌面捷徑可勾選。
- 控制台的「安裝的應用程式」裡有「解除安裝」。
- **你的校準與樣板（`app\config\config.json`、`card_templates\`）是打包在安裝檔裡面的。**
  你只要給對方 `HoloToolSetup.exe` 一個檔，其他什麼都不用另外傳；
  對方裝完這些東西就直接躺在他的資料夾裡，遊戲視窗長寬比一樣的話連校準都免了。

  這兩份標成「已存在就不覆蓋」，**只在重複安裝時才有差別**：
  對方裝了 v1、自己重新校準過，之後你給他 v2 —— 程式碼會更新成新的，
  但他調好的校準與自己抓的樣板不會被你的蓋回去，解除安裝時也不會被刪。
  第一次安裝時他的資料夾是空的，所以一定會完整放進去。
- 你的 `data\`（統計、每日達標次數）與 `logs\` **不會**被打包進去 ——
  那是你自己的紀錄，對方應該從零開始算。

> 💡 打包腳本會先把 `app\dist\HoloTool\` 裡比較新的校準與樣板**搬回專案根目錄**再打包。
> 這一步很重要：PyInstaller 的 `--noconfirm` 會把整個 `app\dist\HoloTool\` 砍掉重建，
> 不先搬走的話，你在 exe 那邊蒐集的樣板會在打包當下全部消失。
> 保險起見它也會另外留一份 `app\dist\HoloTool_backup\`。

## 版本號與自動更新

### 版本號只有一個來源

`app\src\version.py` 的 `__version__`。要發新版就只改這一行：

```python
__version__ = "1.0.1"
```

改完之後這三邊會自動跟著變：GUI 主控台顯示的版本、`build_installer.py` 產生的
安裝檔版本、`make_release.py` 的更新包檔名與更新檢查的比對基準。

> `__version__` 跟 `config.py` 的 `CONFIG_VERSION` **是兩件不同的事**，不要混用。
> 前者是「程式的版本」，後者是「設定檔結構的版本」。程式改了十次但設定檔格式
> 沒動，`CONFIG_VERSION` 就不該動 —— 一動就會讓 `RETUNED_ON_UPGRADE`
> 無謂地覆蓋掉你調過的參數。

同一個檔案裡還有更新來源：

```python
GITHUB_OWNER = "sumy1002"
GITHUB_REPO = "holotool"
```

### 使用者這邊怎麼更新

主控台分頁 →「版本與更新」→ **檢查更新**。

1. 只向 GitHub 問「最新的正式 Release 是哪一版」，不下載任何東西
2. 有新版就跳出說明，你按確認才會繼續
3. 下載 → 校驗 SHA256 → **備份你的校準與樣板** → 解壓到系統暫存區
4. 再問一次「要現在重新啟動嗎」，按是之後程式關閉、外部批次檔置換、自動重開

沒有網路、repo 打錯、GitHub 擋請求時只會在那一行顯示紅字，不會影響其他功能。

### 發一個新版：雙擊 `release.bat`

專案根目錄的 **`release.bat`** 把整個流程包成一次雙擊：

1. 讀出目前版本
2. 把**現有的** `app\dist\HoloTool\` 複製成 `F:\holotool-test-<目前版本>\`
   —— 這份是拿來測更新的「舊版」。`make_release.py` 會把 `app\dist\HoloTool\`
   重新打包成新版本，不先留一份就沒有東西可以更新
3. 修訂號 +1（改的是 `app\src\version.py`）
4. 打包、產生 `HoloTool-<新版本>.zip` 與 `.sha256`
5. 開啟檔案總管選中那兩個檔，並開啟 GitHub 的 new release 頁面（tag 已填好）

你只要把那兩個檔拖進網頁、按 Publish。

想手動控制的話，底下的指令等價：

```powershell
cd F:\holotool
app\.venv\Scripts\python.exe app\packaging\bump_version.py --print   # 看目前版本
app\.venv\Scripts\python.exe app\packaging\bump_version.py --bump    # 修訂號 +1
app\.venv\Scripts\python.exe app\packaging\bump_version.py --set 1.3.0
app\.venv\Scripts\python.exe app\packaging\make_release.py
```

> `bump_version.py` 只會改**行首**那個 `__version__` 定義。`version.py` 的說明
> 文字裡有一行縮排過的 `    __version__ = "1.0.1"` 當範例，那一行不能被動到，
> 有測試 (`test_bump_version.py`) 專門守這件事。

跑完會產生兩個檔並印出後續步驟：

```
app\dist\HoloTool-1.0.1.zip
app\dist\HoloTool-1.0.1.zip.sha256
```

到 GitHub → Releases → **Draft a new release** → tag 填 `v1.0.1` →
把上面兩個檔拖進 Attach binaries → Publish。發布完成，舊版按「檢查更新」
就會看到。

> 想先自己試裝就把 Release 勾成 **pre-release** —— GitHub 的
> `releases/latest` 端點會跳過 pre-release，所以別人按檢查更新不會看到它。
> 試完再取消勾選。

第一次安裝的人要的是安裝檔，加 `--installer` 會順便產生
`HoloToolSetup.exe`，可以一起放上 Release。

### 差分更新包：76 MB → 約 8 MB

`HoloTool-1.0.19.zip` 是 **76.5 MB**，但 1.0.13→1.0.19 六個版本的 zip 大小
**總共只差 54 KB** —— 每次更新有 99.9% 在重抓一模一樣的 numpy / opencv /
tcl-tk / `python3xx.dll`。真正會變的只有 `HoloTool.exe`（裡面包著程式碼）
與 `base_library.zip`。

（順帶一提，`git clone` 整個 repo 只有 909 KB、1.3 秒 —— 覺得「拉更新很慢」
的時候，慢的一定是 Release 資產那 76 MB，不是 git。）

所以 `make_release.py` 每次會多產一個
`HoloTool-<ver>-patch-from-<舊版>.zip`（連同 `.sha256`），發版時**跟整包一起
上傳**。基準線就是 `app\dist\` 裡上一版的整包 zip —— 不需要另外維護清單檔，
比對用 zip 中央目錄現成的 CRC32 + 大小，讀一個 76 MB 的包只要幾毫秒。

updater 光看檔名就知道差分包用不用得上（`-patch-from-<舊版>` 要正好等於
目前安裝的版本），所以**不必先下載任何 metadata**。對不上（跨了好幾版、
或發版時忘了上傳）就安靜地改抓整包。

安全性有兩道關卡：選的時候比檔名，解開之後再比一次 `patch.json` 裡的 `base`。
任何一關不過就整條放棄改抓整包 —— 而放棄的時候安裝目錄一個位元組都還沒被動到。
差分包大於整包的 60% 時（例如真的升級了 opencv）就不產，只出整包。

> **刪除的檔案表達不出來。** 置換用的 `robocopy` 本來就沒有 `/PURGE`，
> 整包更新也不會刪任何東西，所以兩邊行為一致。真的要移除舊檔只能請使用者重裝。

### 更新絕對不會動到的東西

`config\`、`card_templates\`（含 `parts\`）、`data\`、`logs\`、`debug_captures\`。

這件事有**三層**保險，任何一層失效都還有另外兩層：

| 層 | 在哪裡 | 做什麼 |
|---|---|---|
| 1 | `make_release.py` | 更新包裡連這些資料夾都不放進去，而且打包完會自我檢查，發現有就刪掉 zip 並中止發版 |
| 2 | `updater.extract_update()` | 解壓時再過濾一次（也擋 zip 路徑穿越） |
| 3 | 置換用的 `.bat` | `robocopy` 帶 `/XD` 排除，而且**沒有** `/PURGE` 也沒有 `/MIR` |

加上更新前一定會先壓一份 `backups\pre-update-<版本>-<時間戳>.zip`，
**保留最近 5 份**才輪替刪除（只留一代等於白備份 —— 下一次動作就會把唯一
那份好的蓋掉，這個坑踩過了）。

### 為什麼一定要靠外部批次檔

**執行中的 exe 不能覆蓋自己**，Windows 會把檔案鎖住。所以流程是
「下載到暫存 → 解壓 → 關掉主程式 → 由 `.bat` 完成置換 → 重新啟動」，
Python 這一端從頭到尾不去寫 `HoloTool.exe`。

那支批次檔會先用 `tasklist` 等主程式的 PID 真的消失才動手：客氣地等 15 秒，
還在就 `taskkill` 強制關掉，再撐到 35 秒都關不掉就放棄並且**完全不動**安裝目錄。
程式端也不是只呼叫 `destroy()` 就算了 —— 最後一定會走
`updater.hard_exit()`（`os._exit`）確保行程真的結束。

> 這兩層是同一個坑的正反面：只要「視窗關了但行程還活著」，.bat 就會一直等一個
> 永遠不會消失的 PID，畫面就停在一個什麼都不做的黑視窗上。實際踩過。

過程寫在 `app\logs\update.log`，更新出問題就先看這個檔。
批次檔內容**一律只用 ASCII** —— cmd 預設不是 UTF-8，帶中文的批次檔在某些
機器上會整行解析失敗，非常難查。

### 開發模式不支援自動置換

直接跑 `gui.py` 時「檢查更新」還是會告訴你有沒有新版，但不會自己置換檔案
（沒有 exe 可以換）。原始碼請用 `git pull`。

## 這個專案與 GitHub

repo 是**公開**的，所以自動更新的下載不需要任何 token，`HoloTool.exe` 裡
也沒有藏任何憑證。

### 什麼進版控、什麼不進

| | 進版控 | 說明 |
|---|---|---|
| `gui.py`、`app\src\`、`app\tools\`、`app\packaging\`、`app\tests\`、`app\docs\` | ✅ | 程式碼與文件 |
| `app\defaults\` | ✅ | 內建預設樣板，屬於程式內容 |
| `app\config\config.json` | ❌ | 你逐格校準的座標，綁著你自己的視窗解析度，對別人沒用 |
| `app\card_templates\` | ❌ | 你在實機抓的樣板。**這是重點** —— 一旦進版控，任何 `git pull` / `git checkout` 都有機會蓋掉它 |
| `.venv\`、`dist\`、`build\`、`logs\`、`data\`、`debug_captures\`、`backups\` | ❌ | 環境、產物、紀錄 |

> `app\defaults_layout.py` 已經帶著你在 1843×778 量出來的比例值
> （五格手牌是逐格量的，間距並不等寬），所以就算不把 `config.json` 進版控，
> 重灌或別人第一次裝也會拿到相當接近的預設框選。

### 想把自己抓的樣板分享出去

別直接把 `card_templates\` 加進版控。用這支工具**複製**一份到
`app\defaults\parts\`（那是程式內容，會進版控也會進更新包）：

```powershell
app\.venv\Scripts\python.exe app\tools\promote_templates.py           # 先預演，不動任何檔案
app\.venv\Scripts\python.exe app\tools\promote_templates.py --apply   # 確認後真的複製
```

複製過去時會改名成 `rank_2_b1.png` 這種帶 `b` 的編號，讓你原本那些檔案繼續
被歸類成「你自己的樣板」，辨識行為完全不變。之後別人裝好時，
`install_default_parts(overwrite=False)` 會把它們複製到他的
`card_templates\parts\` —— **不會蓋掉他自己抓的任何東西**。

### 第 1 步：校準座標

1. 手動把遊戲開到「High & Low 牌桌畫面」（可以看到開始/下注按鈕的畫面）。
2. 執行：

   ```powershell
   app\.venv\Scripts\python.exe app\tools\calibrate.py
   ```

3. 依畫面指示輸入遊戲視窗標題關鍵字，然後依序框選/點擊：
   - 牌桌標記區域（一塊只有在這個牌桌畫面才會出現的獨特小區塊，例如標題文字/圖示）
   - 5 張手牌區域（門票關卡）
   - 比大小環節目前亮牌的區域
   - 開始/下注、確認換牌、大、小、收集/兌現 按鈕
   - 5 張手牌各自的「保留/丟棄」切換點擊位置（多數遊戲點卡面本身就能切換）

校準結果會存到 `config/config.json`，可以直接用文字編輯器打開微調數值。

**關於視窗大小**：所有座標都以「比例值 (0~1)」儲存，代表相對於視窗寬/高的百分比位置，
所以校準完之後你可以**自由移動與縮放視窗**，不需要重新校準，程式會依視窗當下的
實際尺寸即時換算。但要注意：

- **長寬比改變時會自動換算座標**。遊戲的 UI 排在一個置中的 16:9 內容框裡（見上面
  「視窗長寬比」），所以換比例時程式會從最接近的那組**算**出正確座標，誤差 1~4 像素，
  不需要重新校準。誤差在 `aspect_ratio_tolerance`（預設 2%）以內算同一種比例、直接沿用。
- **不要縮得太小**。視窗越小，每張牌的像素越少，不同牌的樣板分數會越靠近而難以區分。
  建議讓每張牌至少保有 60～80 像素寬；縮到校準時的 0.6 倍以下時程式也會提醒你。
- **不能最小化，也不能被其他視窗蓋住**，因為程式是直接讀取螢幕上那塊區域的像素。

### 第 2 步：蒐集點數與花色樣板

工具是用「讀卡片左上角的點數 + 花色」來辨識牌面，所以**不必蒐集 52 張整卡**，
只要湊齊 **13 個點數 + 4 個花色 = 17 個小圖**，全部 52 張牌就都認得出來。
一手牌就有 5 張，玩個一兩局大概就齊了。

推薦用 GUI 的「點數/花色樣板」分頁：

1. 玩到選牌畫面（五張牌正面朝上）
2. 按「讀取目前畫面」——程式會自動把五張牌的左上角切出來，並用現有樣板猜出牌面
3. 猜對的直接留著，猜錯或空白的自己填（例如 `10H`、`AS`、`QD`）
4. 按「全部儲存」

代號欄**只吃英數字，大小寫沒差**（`10h` 跟 `10H` 一樣），全形的 `１０Ｈ` 也會自動
折成半角。而且那六格已經**關掉輸入法**了 —— 以前每按一次「讀取目前畫面」，
Windows 就把輸入法切回中文（剛剛用 Shift 切成英文的狀態不會跟著焦點走），
每抓一輪牌都要重切一次；現在打什麼字就直接進來，跟輸入法目前是中英文無關。

「蒐集進度」收在下面，預設收合，點標題那一列就能展開。
六格「這一輪抓到的牌」會依視窗寬度自動換行，整頁也包在捲動區裡 ——
以前視窗縮小的時候，那六格會被右邊的「蒐集進度」擠掉而且捲不過去。

存數字牌時，程式會**額外把卡面中央那個大花色圖案也存起來**。角落那顆花色只有
十幾像素，黑桃和梅花常常只差 0.01 分；中央那個大三四倍，是把兩者分乾淨的關鍵。

#### 鬼牌（Joker）也要抓，代號填 `JK`

這副牌有鬼牌。它的左上角印的不是點數字，而是一個 **`$`**（右下角一樣印一次，
轉 180 度），版面跟其他 52 張牌完全一樣，所以只要把它當成**第 14 個點數**存起來
就認得出來 —— 在那一格填 `JK` 再按「全部儲存」即可。
鬼牌**沒有花色**，程式只會存左上角那個 `$` 當點數樣板，不會存花色與中央大圖案。

> 為什麼一定要抓：鬼牌的 `$` 對 13 個點數的分數全部落在 **0.6 上下**
> （實機 log：`點數 8=0.64 2=0.62 ←分數未達 0.72`），正解根本不在候選名單裡，
> **調任何門檻都救不了**（真的調到 0.6 反而開始把真牌認錯）。
> 沒有鬼牌樣板的話，抽到鬼牌那一格永遠認不出來，選牌畫面卡在 4/5。
>
> 專案已內附一組從實機截圖切出來的鬼牌樣板（`defaults/parts/rank_JK_1.png`、
> `rank_JK_2.png`），所以多數人不用自己抓；抓幾張自己的會更準。
> 實測：雙角交叉驗證 JK=0.80、第二名 8=0.66（領先 0.14）；
> 另外 42 格真牌加入鬼牌樣板後判讀結果**一格都沒變**（鬼牌樣板對真牌最高只有 0.66）。

> 專案已內附一組從截圖做出來的預設樣板（12 個點數 + 4 個花色，只缺「5」），
> 第一次執行會自動複製到 `card_templates/parts/`。可以直接開始用，
> 但**強烈建議在自己的實機畫面重新蒐集一輪**，準確度會明顯提升。

#### 內建樣板 vs 你自己抓的樣板

內建樣板是從 512～1024 寬的縮圖放大來的，筆畫比實機糊一圈。混在一起比對時，
糊掉的「7」有可能比清楚的「2」更像你螢幕上那個 2 —— 這就是「2、5、8 一直跳問號」
和「黑桃梅花分不清」的來源。

所以某個標籤**自己抓的樣板累積到 3 張以上**之後，那個標籤的內建樣板就整組不用。
**在那之前是「你的 + 內建」混著用** —— 只有 1 張自己的就丟掉內建那 8 張，
結果比混著用還糟很多（實測見下）。

要不要丟內建是**整個比較組一起決定**的：花色是先用顏色縮成兩個候選才比形狀，
所以 H 只跟 D 競爭、S 只跟 C 競爭。如果 H 有 3 張、D 只有 1 張就各自決定，
會變成「3 張清楚的 H vs 1 張清楚的 D + 8 張糊的 D」—— 一場偏向錯答案的比賽。

「蒐集進度」會列出**每個標籤自己抓了幾張**、還差幾張才會丟內建，
以及有沒有裁切壞掉的檔案；右邊清單會標「（內建）」與「← 裁切壞掉，不會用」。
全部抓齊之後可以按「清掉所有內建樣板」把內建的一次刪光（你自己抓的不會動 ——
這裡是**比檔案內容**判斷的，不是比檔名，原因見下）。

#### 2026-08-21：為什麼以前「多抓幾次」完全沒有用

使用者回報「我輸入或修改很多次，但看起來好像都沒變化」「有時候方塊會被認為是愛心」。
拿他實機的 67 個樣板量出來，是**四個獨立的 bug 疊在一起**：

| # | 問題 | 後果 |
|---|---|---|
| 1 | 「哪些是內建的」只比**檔名** | 內建檔叫 `suit_D_1..8.png`，而新檔挑「空著的最小編號」，於是他自己抓的樣板被寫進一個「看起來像內建」的檔名 —— **下一次儲存會把上一次的成果當成內建檔刪掉**。67 個檔案裡有 19 個是這種 |
| 2 | 同一批檔案在比對時也被丟進 fallback 桶 | 存了等於沒存 |
| 3 | `part_is_usable` 在 `centre_mask` **之後**才判斷 | centre_mask 是平移，貼邊的圖案平移後被切掉一角、佔滿度掉下來，好樣板被判成「裁壞的小點」而安靜丟掉（誤殺 6 張） |
| 4 | 「自己的有 1 張就丟掉內建 8 張」 | 他的 suit_D 只剩 1 張能用，**方塊只能拿 1 張去跟 3 張紅心比** ← 這就是方塊被認成愛心的直接原因 |

留一法實測（查詢與樣板都用他實機的圖）：

| | 角落花色 | 點數 | 整體 |
|---|---|---|---|
| 修好前 | 78.1% | 88.4% | **88.7%** |
| 修好後 | **100%** | 95.3% | **96.8%** |

修好後**花色錯誤全部消失**（不再有 D→H、C→S）。剩下的 2 個都是點數，
而且都是「花色符號的一小角被留在點數框裡」的髒樣板 —— 刪掉重抓即可。

順帶修的三件事：

* **儲存流程完全不再刪檔**。「存自己的就順手刪內建的」原本是為了繞開舊的名額
  bug，但它自己變成上面第 1 條的一半，而且會抽掉第 4 條需要的墊背。
* **點數小圖會去掉雜點**（面積小於最大連通塊 8% 的獨立小塊）。角落的點數與花色
  是靠橫向投影切開的，常常把花色的一角留在點數那一塊裡，質心置中就被拉歪。
  「10」是兩塊所以用比例而不是「只留最大塊」；花色**不做**（梅花本身就是好幾瓣，
  實測門檻拉到 10% 以上就會把真正的花色瓣切掉）。
* **同一個標籤的上限從 8 張放寬到 16 張**。比對是取最高分，多存只會更容易命中；
  他的 `rank_5` 早就存滿 8 張、再抓也存不進去。

> ⚠️ 2026-08-20 修掉的一個老 bug：內建樣板每個花色剛好 8 張，而「同一個標籤最多留
> 8 張」的上限把內建的也算進去 —— 於是花色**一開始就是滿的**，按幾次「全部儲存」
> 都不會存下任何花色，畫面還完全不報錯。點數只有 3~4 張內建所以存得進去，
> 症狀才會變成「點數會學、花色永遠學不會」。現在上限只算你自己抓的
>（存檔也不再刪任何檔案，見上面「順帶修的三件事」）。
> **如果你之前存過花色卻覺得沒效果，就是踩到這個，請再存一次。**

實機 log：

那張是 8♦。花色判得又快又對（0.97 對 0.78），**點數的第一名也是對的**，

問題不在門檻高低，在於**比大小畫面沒有任何畫面標記**：讀不到牌不會退回別的判斷，

| | 代價 |
|---|---|
| 猜錯點數 | 這一次大小猜壞（而且本來就要求連續兩次讀到同一張才動作） |

## 策略邏輯說明

- **選牌（門票關卡）**：點「要留下的牌」（出現「剩餘」），沒點的會被「替換」。
  對 32 種保留組合模擬換牌後「至少兩對」的機率。鬼牌 JK 當萬能牌。
- **過關後**：先點「點擊繼續」，再在「要挑戰嗎？」選「進行挑戰」或「取消」兌現。
- **比大小**：只能選「大」或「小」。畫面寫「數字相同時，再抽一次」，平手不計勝負。
  要不要繼續加倍是在贏了之後的對話框決定，不是在大/小畫面上。
- **機率估計**：採用貝氏平滑 —— 資料不足時退回標準 52 張牌均勻機率，資料越多
  越貼近「今天實際觀察到的出牌分布」，並用過去幾天的紀錄作為很弱的輔助參考。
  每日統計檔案存在 `data/stats_YYYY-MM-DD.json`，可以自行打開查看。

### 「補算未記錄的數值」：讓機率模型吃到全部的牌

機率估計吃的是 `stats_YYYY-MM-DD.json` 的 `card_counts`，而那份計數只有在 bot
正常跑到「選牌階段 / 比大小階段」時才會 +1。實際上有好幾條路會漏：

- **exe 版與原始碼版各有一份 `data\`**。平常跑 `dist\HoloTool\HoloTool.exe`，
  統計寫在它自己的 `app\data\`；偶爾用原始碼跑一次，那一份完全看不到對面累積的
  資料 —— 同一天的牌被拆成兩本帳，兩邊的機率都偏保守。
- **只開「顯示即時辨識」看畫面時**牌是認出來了，但沒有經過 `_handle_*`，一張都不會記。
- **程式中途被關掉或當掉**，那一輪的牌只留在 log 裡。

主控台「今日統計」那顆 **「補算未記錄的數值」** 就是把這些補回來：

- 掃 `logs\bot_YYYY-MM-DD.log` 的 `[選牌階段] 手牌=(...)` 與
  `[比大小階段] 目前牌=X`（**只認這兩種「狀態變了才印一次」的行**；
  `偵測中 ... 比大小=6C` 每個 tick 印一次，算進去會讓同一張牌暴增十幾倍）。
- 併入 `dist\` 底下其他安裝的 `data\`（裝到別處的那份寫進 `extra_data_dirs`）。
- 今天與**前 6 天**都掃 —— 歷史紀錄是機率模型的弱先驗，前幾天補回去，今天也會更準。

兩個保證：**可以重複按**（log 記「掃到第幾行」、外部統計記「上次的計數快照」，
所以第二次按會回報「無其餘資料」）、**只增不減**（log 被清掉或對面統計被砍掉，
既有的數字原樣保留）。實作在 `app\src\reconcile.py`，
`app\tests\test_reconcile.py` 有 14 個測試守著這兩件事。

## 設定檔 `config/config.json` 常用欄位

| 欄位 | 說明 |
|---|---|
| `ace_high` | 比大小時 A 是否視為最大牌 |
| `part_min_score` | 點數/花色小樣板的比對門檻，預設 0.72（加了質心對位後真正在把關的是下面的領先幅度） |
| `part_min_margin` | 點數最高分需領先第二名多少才採信，預設 0.05 |
| `match_threshold` | （備援用）整張卡面比對的相似度門檻。預設 **0.2**：真正在把關的是 `part_min_score`／`part_min_margin`，這個門檻訂高等於讓備援永遠不生效。`config_version` 5 會把舊設定檔裡的值強制換成 0.2 |
| `min_match_margin` | （備援用）整張卡面比對的領先幅度門檻 |
| `calibration` | 目前生效那一組校準當時的視窗尺寸（校準時自動寫入） |
| `aspect_ratio_tolerance` | 長寬比容許誤差，誤差在此以內算同一種比例，預設 0.02（2%） |
| `calibration_profiles` | 每種長寬比一組校準（label / client_width / client_height / regions / points）。`derived_from` 有值代表是換算出來的。不要手改，用主控台的「視窗比例」區塊 |
| `active_profile` | 目前生效的組別 label。`null` 代表正在借用別的比例的座標 |
| `auto_detect_profile` | 選好視窗（或視窗被拉成別的比例）時自動偵測比例並套用對應校準。在主控台手動指定比例時會變成 `false` |
| `extra_data_dirs` | 「補算未記錄的數值」要一起併入的其他 `data\` 資料夾（絕對路徑）。`dist\` 底下那幾份程式會自己找 |
| `mini_panel` | 迷你懸浮視窗上次的位置 `{x, y}` |
| `templates.capture_client_width` | **擷取六個畫面標記樣板時的視窗寬度**。樣板是點陣圖，比對前會依「目前視窗寬 ÷ 這個值」縮放；重新框選標記時會自動更新 |
| `marker_thresholds` | 六個畫面標記各自的比對門檻（牌桌/選牌/過關/翻倍/失敗/湊牌失敗） |
| `marker_pads` | 各標記往外擴張搜尋的量 `[左右, 上下]`，單位是該區域自身的寬/高比例 |
| `draw_prompt_soft_threshold` | 選牌文字分數只到這裡、但五張手牌都認得出來時，一樣算選牌畫面 |
| `exit_table_ticks` | 連續幾次看不到牌桌 logo 才判定已離開牌桌（預設 25，約 10 秒） |
| `draw_result_wait_sec` | 按完「替換」之後最多安靜等幾秒讓遊戲切畫面（預設 15）。這段期間不做任何判斷；超時也只是回到一般偵測，**不會**自己當成湊牌失敗 |
| `config_version` | 設定檔版本。升級時某些「重新調校過」的參數會強制換成新預設（目前是 `part_min_score` / `part_min_margin`），校準數值一律保留不動 |
| `daily_max_wins` | 每天可以達到「最高獲得金額」幾次（遊戲規則是 2）。達成次數記在 `data/stats_YYYY-MM-DD.json` 的 `max_win_count`，重開程式也不會重數；手動玩過導致次數對不上就直接改那個檔案 |
| `highlow_scan_right` | 比大小掃描「目前這張牌」時，往右掃到畫面的哪個比例位置為止 |
| `table_marker_threshold` | 舊欄位，已由 `marker_thresholds.table_marker` 取代 |
| `monte_carlo_samples` | 選牌策略模擬次數，越大越準但越慢 |
| `highlow_min_win_prob_to_continue` | 比大小勝率低於此值就收手兌現 |
| `highlow_max_chain` | 比大小最多連續加倍幾次 |
| `capture_interval_sec` | 主迴圈偵測間隔秒數 |
| `action_cooldown_sec` | 點完之後至少等多久才做下一個動作（預設 1.2 秒）。遊戲跑得慢就調大 |
| `action_retry_sec` | 同一個畫面卡多久沒變，就視為遊戲漏收點擊而再點一次（預設 2.5 秒） |
| `idle_confirm_sec` | 畫面要連續認不出來多久，才會去點「投注並開始」（預設 1.5 秒） |
| `multi_click_gap_sec` | 選牌時連點五張牌，每一下之間的間隔（預設 0.18 秒） |
| `click_hold_min_sec` / `click_hold_max_sec` | 滑鼠按下到放開的停留時間（預設 0.06~0.12 秒） |

## 已知假設 / 之後可能需要調整的地方

因為我沒有你實際的遊戲畫面，下列邏輯是根據你描述的規則所做的假設，實際測試後
若發現跟遊戲行為不符，歡迎直接告訴我，我可以再調整程式：

1. **換牌次數**：目前假設「門票關卡只能換一次牌」（發5張→選保留/丟棄→補牌後直接
   定局）。若實際上可以換多次，需要調整 `_handle_draw_phase` 的流程。
2. **確認/前進按鈕**：換完牌之後如果需要額外按一次「確認」才能進入比大小畫面，
   目前程式重複使用 `draw_confirm` 這個按鈕，若實際上是不同按鈕，需要在
   `config.json` 的 `points` 裡新增並修改 `src/bot.py` 對應的呼叫。
3. **比大小的目標是「衝到 12800 上限」，不是「期望硬幣數最大」**。
   這兩個目標會導出完全相反的行為：中途兌現拿走 400 枚，帳面好看，
   但這一輪就**永遠到不了 12800**。所以預設是
   `highlow_min_win_prob_to_continue = 0`（永遠不收手）＋
   `highlow_max_chain = 0`（不設連勝上限，讓遊戲自己在 12800 喊停）。
   想改回「賺硬幣」的玩法就把這兩個調回 0.5 與 6。

   **平手規則**：同點數會重抽、不計勝負，所以平手那一塊機率既不算贏也不算輸，
   `decide_high_or_low` 回報的是「**有勝負時**猜中的機率」。以前分母含平手，
   系統性低估 —— 一副均勻的牌拿到 8 會回 6/13 = 0.462，看起來像爛賭注，
   實際上是 6/12 = 0.500 的公平硬幣。實機 log 出現過
   `目前牌=8H 預估勝率=47.1% → 取消兌現`，就是這兩件事疊在一起。
4. **是否為固定52張牌無重複抽取**：換牌模擬時假設「目前看到的5張牌」在這一輪
   內不會重複出現（無重複抽取），但比大小的機率估計則是用「今天觀察到的頻率」
   獨立估計每張牌出現機率（不特別排除已出現過的牌），這是因為你希望依實際出牌
   頻率推算機率、而非假設固定的實體牌堆。
5. **每日上限偵測**：主要靠「已達最高獲得金額，遊戲結束」這一行字（`max_win_marker`），
   第 1 次自動按「再玩一次」、第 2 次自動停止。「牌桌標記區域消失」則保留為備援。
   這個標記以前**沒有**內建預設樣板（拿不到那個畫面的原生像素），
   所以狀態列一直是「上限=無」、`_handle_max_win()` 一次都沒執行過。
   2026-08-21 用主控台的「存一張目前畫面（PNG）」抓到原生截圖之後補上了 ——
   實測 4 張上限畫面 0.810~0.988、另外 21 張其他畫面最高 0.616，門檻 0.71。
   正常情況**不需要自己校準**；`app\tools\check_setup.py` 仍然會檢查。

   > 那顆按鈕上的字是「**結束**」，不是「再玩一次」（設定裡的名稱沿用舊的）。
   > 按下去會回到牌桌，還在每日額度內就能繼續玩。
6. **縮放後的辨識能力**：牌面辨識是讀左上角的點數與花色，會依卡片實際大小自動
   換算，所以縮放沒問題；但視窗太小時字會糊掉。建議每張牌至少留 60~80 像素寬。
7. **比大小剛翻牌的瞬間**：那一張會放大並超出校準框，這個過渡畫面會回報「認不出來」，
   等它落回牌列後才讀得到。這是刻意的：寧可等 0.4 秒，也不要讀錯牌。

## 疑難排解

### 先跑這兩個指令

```powershell
app\.venv\Scripts\python.exe app\tools\check_setup.py                          # 還缺什麼
app\.venv\Scripts\python.exe app\tools\check_markers.py app\debug_captures    # 六個標記各拿幾分
```

`app\tools\check_markers.py` 是離線工具，不用開遊戲，拿現成截圖就能算出每個畫面標記的分數，
右邊標 `*` 代表超過門檻。可以加 `--width 1937` 模擬「實機視窗這麼寬時的分數」。

### 常見狀況

- **打包 / `release.bat` 丟「PyInstaller 失敗（結束碼 1）」**：最常見的原因是
  **HoloTool 還開著**。PyInstaller 的 `--noconfirm` 會把整個 `dist\HoloTool\`
  砍掉重建，而執行中的 exe / dll 刪不掉 —— 前面 Analysis、PYZ、EXE 全部成功，
  只有最後一步 COLLECT 失敗，所以看起來很像「打包壞掉」。
  把主視窗**和「縮成迷你視窗」那個小方塊**都關掉（它沒有標題列也不在工作列，
  最容易忘記），再重跑一次就好。
  現在 `build_exe.py` 會在開工前先探測一次，被鎖住就立刻中止並列出是哪個檔案，
  不會讓你等三分鐘才換到一個結束碼。PyInstaller 的完整輸出也一律留在
  `app\packaging\build\pyinstaller-last.log`，失敗時會直接印出最後 30 行 ——
  終端機回捲緩衝區蓋掉了也還查得到。

- **畫面標記全部認不出來（分數都在 0.4~0.7 徘徊）**：多半是**樣板解析度和實機視窗
  對不上**。內建預設樣板是從 1024×438 的截圖切出來的；如果你的遊戲視窗是
  1937×817，樣板要放大 1.89 倍才對得起來。程式會依
  `templates.capture_client_width` 自動換算，但這個值必須正確。

  最乾淨的做法：在「校準」分頁對著實機畫面**逐項重新框選**六個畫面標記
  （框完當下就會用目前解析度重存樣板，並自動更新這個欄位）。

  ⚠️ 重存之後**不要再按「套用截圖預設框選」**，那顆按鈕會把樣板整組還原成
  1024 寬的內建預設圖，等於白做。

- **對話框停久了就自動停止、說「已達每日次數上限」**：翻倍/成功/失敗這些對話框會把
  整個牌桌連同左上角 High&Low logo 一起模糊掉，logo 認不出來是正常的。程式已經會在
  偵測到任一對話框時重置離桌計數器；若還是誤判，把 `exit_table_ticks` 調大。

- **湊牌結果畫面有時認得、有時認不得**：那個位置的大標題是會變的
  （失敗／無對子／一對／兩對…），所以不能只靠 `fail_marker`。真正不變的是副標
  「要再玩一次撲克嗎？」，也就是 `poker_fail_marker`。若這個標記分數偏低，
  優先重新框選它。

- **程式以為點了、但遊戲沒反應，然後就卡住不動**：遊戲跑得比程式慢時會漏收點擊。
  程式現在會在同一個畫面卡超過 `action_retry_sec`（預設 2.5 秒）時自動再點一次，
  log 會出現「[重試] 畫面還停在…」。如果還是常常卡住，依序調整：
  1. `click_hold_min_sec` / `click_hold_max_sec` 調大（例如 0.10 / 0.20）——
     讓滑鼠按住的時間橫跨更多幀，這通常最有效
  2. `action_retry_sec` 調小（例如 1.8），卡住時更快補點
  3. `multi_click_gap_sec` 調大（例如 0.30），選牌那五下之間留更多時間

- **明明湊到牌了，卻跳「湊牌失敗」把那一局打掉**：舊版會在按完「替換」之後等 2.5 秒，
  沒看到過關畫面就自己認定湊牌失敗。遊戲慢一點就會誤判。現在**只認
  「要再玩一次撲克嗎？」這個標記**，看不到標記就安靜等（最多
  `draw_result_wait_sec`，預設 15 秒），超時也只是回到一般偵測，不會亂點。

- **某幾個點數一直跳問號（常見於 2、5、8），或黑桃梅花分不清**：
  1. 先看「點數/花色樣板」分頁的「蒐集進度」，有沒有標「還在用內建樣板」。
     有的話在實機畫面抓一次自己的，程式會自動改用你的。
  2. 程式會同時讀**左上角和右下角**兩個角落（撲克牌的點數花色一定印兩次），
     兩次分數平均之後雜訊會互相抵銷。比大小畫面的牌被疊住、只露左上角時
     會自動退回單角判讀，log 會註明「只讀得到左上角」。
  3. 還是不行就把 `part_min_margin` 調小一點（例如 0.03）。

- **會多點一下「投注並開始」，把畫面弄亂**：那是遊戲在跑動畫、畫面暫時認不出來時
  被誤判成待機。把 `action_cooldown_sec` 或 `idle_confirm_sec` 調大（例如 2.0）。

- **達到上限了卻沒自動停／沒按「再玩一次」**：先跑 `app\tools\check_setup.py` 看
  「已達最高獲得金額標記」是不是還沒校準。校準時要框**底部中央那一行字**
  （「已達最高獲得金額，遊戲結束」），不要框到旁邊的按鈕；右下角那顆「再玩一次」
  的位置跟失敗畫面那顆不一樣，要另外校準 `max_win_retry`。

- **今天的達成次數算錯了**（例如自己先手動玩過一次）：打開
  `data/stats_YYYY-MM-DD.json`，把 `max_win_count` 改成正確的數字即可。

- **改了 `__version__`，打包出來卻還是舊版本號**：**先確認你開的是哪一個 exe。**
  重新打包只會更新 `F:\holotool\app\dist\HoloTool\HoloTool.exe`。
  如果你之前跑過 `HoloToolSetup.exe`，那份裝在 `%LOCALAPPDATA%\HoloTool`
  的複本（以及安裝程式建立的開始選單／桌面捷徑）**不會**因為重新打包而改變。
  `build_exe.py` 現在會在開頭與結尾各印一次版本號和該開哪個路徑。

- **按「檢查更新」說找不到 repo（HTTP 404）**：`app\src\version.py` 的
  `GITHUB_OWNER` / `GITHUB_REPO` 打錯，或那個 repo 還沒發過任何 Release。
  用瀏覽器開 `https://github.com/<OWNER>/<REPO>/releases` 確認一下。

- **按「檢查更新」說 GitHub 擋住請求（HTTP 403）**：未登入的 API 查詢每小時有
  次數上限。等一小時，或直接到 Release 頁面手動下載。

- **更新後停在一個黑色命令列視窗不動**：那是置換腳本卡在「等主程式關閉」。
  視窗標題會是 `find "<某個數字>"`。**此時 `robocopy` 還沒跑，什麼都沒被改**，
  直接關掉那個視窗，再到工作管理員確認沒有殘留的 `HoloTool.exe` 就好。
  這個情形在 1.0.1 之後修掉了（程式端強制結束行程、腳本端等不到就 taskkill）。

- **按下更新之後 HoloTool 關掉，然後就再也沒有出現**（工作管理員裡也沒有）：
  複製那一步失敗了，而**舊版的置換腳本在失敗時不會把程式叫回來** ——
  所以畫面上什麼都不剩，看起來像整個消失。

  1. 先直接雙擊 `HoloTool.exe`，多半打得開（你的校準與樣板一定沒被動到，
     那幾個資料夾在三層防護裡）。
  2. 看 `app\logs\update.log` 最後一段：`robocopy exit code 16` 就是
     **沒有寫入權限**，最常見的原因是裝在 `C:\Program Files` 底下。
  3. 打不開的話到 Release 頁面下載 zip，手動解壓覆蓋安裝資料夾即可
     （zip 裡不含 `config\`、`card_templates\`，覆蓋不會蓋掉你的東西）。

  1.0.18 之後三邊都補起來了：

  * **更新前**先實際在安裝資料夾寫一個探測檔，寫不進去就在**還沒關掉程式**的
    時候擋下來並說明原因。
  * 置換腳本**複製失敗時會把舊版重新開起來**，不會再留一個空桌面。
  * 啟動腳本改用 `CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_CONSOLE`（見下一條）。

- **湊到牌的「過關」畫面有時候認不出來、卡住**（其他標記分數也整排偏低）：
  縮放基準錯了。`templates.capture_client_width/height` 記的是「這幾張標記圖是
  在多大的畫面下截的」，跟圖的真實來源對不上時，比對前就會縮放到錯的倍率。

  實機量過的差距（同一張過關截圖）：

  | 基準 | 過關分數 |
  |---|---|
  | 1024×438（設定檔裡的舊值） | **0.69** ← 門檻 0.80，過不了 |
  | 1365×576（圖真正的來源） | **1.00** |

  1.0.18 起 `load_config()` **每次載入**都會檢查（以前只在升級那一次），
  七張標記全部都是內建原封複本時就自動把基準同步成 1365×576；
  只要有一張是你自己抓的就整組不動。啟動 log 也會講：
  `[樣板] 畫面標記混著兩種來源…` / `[警告] …設定檔卻寫著 1024x438`。

  自己抓的標記與內建的混在一起時，那**一個**基準只能對其中一邊。
  要乾淨就在「校準」分頁把七張都重新框選一次。

- **狀態列一直是「上限=無」，達到上限也不會自動按按鈕**：
  `card_templates\ui_max_win.png` 不見了。它是唯一一張「內建有、但要靠程式
  複製到 `card_templates\`」的標記（那個資料夾不進版控也不進更新包）。
  1.0.18 起 `prepare_runtime()` 每次啟動都會把**缺少的**內建標記補回去
  （`overwrite=False`，不會蓋掉你自己重新框選的），所以重開一次就好。
  仍然沒有的話，確認 `app\defaults\ui\ui_max_win.png` 在不在。

  「無」跟「分數很低」是兩件事：**無 = 根本沒有那張樣板可以比**，
  調門檻沒有用。

- **`update.log` 只有最前面那幾行標頭，連 `==== done ====` 都沒有**：
  腳本被**連坐殺掉**了。主程式如果被放在一個 `KILL_ON_JOB_CLOSE` 的 job 物件裡
  （某些啟動器、防毒、遠端桌面工作階段都會這樣做），子行程預設會繼承那個 job，
  主程式 `os._exit()` 的瞬間腳本就跟著死，而且**完全沒有錯誤訊息**。

  1.0.18 起啟動旗標改成
  `CREATE_BREAKAWAY_FROM_JOB | CREATE_NEW_CONSOLE | CREATE_NEW_PROCESS_GROUP`，
  job 不給脫離時再退成單純的新視窗、最後才退回舊的 `DETACHED_PROCESS`，
  而且會把實際用到的那一種寫進主程式的 log（`[更新] 置換腳本已啟動（…）`）。

  > 順帶更正一個一直寫錯的註解：`DETACHED_PROCESS` 是**完全沒有 console**，
  > 不是「開一個新的」。所以對話框說的「畫面會閃一下命令列視窗」以前從來沒有
  > 兌現過，腳本裡沒有導向檔案的 `echo` 也全部丟進虛空 —— 要看得見的視窗
  > 得用 `CREATE_NEW_CONSOLE`。

  等待迴圈現在**每一拍都寫一行 log**（`[WAIT] tick n`），所以下次真的再出事，
  「腳本沒動」跟「主程式關不掉」一眼就分得出來。

- **更新按完重開，版本還是舊的**：看 `app\logs\update.log`。
  常見兩種：`pid ... would not exit`（主程式關不掉 —— 通常是還有另一個
  HoloTool 視窗開著）、`robocopy exit code ...`（安裝目錄沒有寫入權限，
  例如裝在 `C:\Program Files` 底下）。兩種都不會動到你的校準與樣板，
  重跑一次或改用安裝檔手動更新即可。

- **更新之後想確認校準沒被動到**：看 `app\backups\` 裡最新那個
  `pre-update-*.zip`，跟現在的 `config\config.json`、`card_templates\parts\`
  比一下。備份留最近 5 份，要還原就直接解壓覆蓋回去。

- **F9/F10 沒反應**：改用系統管理員身分執行終端機。
- **辨識不到牌**：先跑 `app\tools\check_setup.py` 看「點數 x/13、花色 x/4」還缺什麼。缺的那些
  牌一定認不出來。接著用 `--dry-run` 模式觀察 log。可能是視窗縮太小導致各張牌分數
  太接近而被 `min_match_margin` 保護機制擋下（這是刻意設計：寧可辨識失敗也不要
  猜錯牌）。解法是把視窗放大一點，或補充更多卡牌樣板；真的要放寬才調低
  `match_threshold` / `min_match_margin`。
- **樣板都蒐集齊了，執行時卻只認出 2/5**：這是對位問題，不是樣板不夠。
  同一個點數在不同影格切出來的位置常常差一兩像素，重疊度就會掉 0.15~0.20 分。
  程式現在會先把字的「質心」對到畫布正中央，再做 ±1 像素的微調才比對 ——
  實測正解分數中位數從 0.78 拉到 0.97。
  現在辨識失敗時 log 會直接印出原因，例如：

  ```
  已看到選牌畫面，但手牌只認出 2/5，以下是認不出來的那幾格：
     第 3 張：點數 9=0.78  7=0.69 ←領先不足 0.05 | 中央大圖案(黑) C=0.95  S=0.93
  ```

  「←分數未達」就是缺那個點數/花色的樣板；「←領先不足」就是兩個候選太像，
  在「點數/花色樣板」分頁多存幾張那個點數即可。

- **某一格永遠認不出來、每個點數都只有 0.6 上下**：那一格多半是**鬼牌**。
  log 會直接這樣講：

  ```
     第 2 張：點數 8=0.66  6=0.65 ←分數未達 0.72 | （都不像 → 這一格如果是鬼牌，
              請到「點數/花色樣板」讀取畫面、代號填 JK 再儲存；門檻不用調）
  ```

  **不要調門檻** —— 正解不在候選名單裡，調再低也不會出現，只會開始認錯真牌。
  正確做法是抓一張 `JK` 樣板（見上面「鬼牌也要抓」）。

- **五張沒認齊，bot 就永遠停在選牌畫面**：這是舊行為，已經修掉。
  現在同一組認不齊的判讀連續維持 `partial_draw_rescue_sec`（預設 20 秒）之後，
  程式會只用**認得出來的牌**做最保守的決定（有對子留對子，否則五張全換）
  並按「替換」讓流程繼續跑，同時在 log 大聲說明：

  ```
  [選牌自救] 第 [2] 張已經連續 20 秒認不出來，不能一直停在這裡。
             改用認得出來的 ['2H', 'AH', 'QS', '3D'] 做決定：沒有對子，五張全換。
  ```

  這是止血不是根治 —— 這一局的期望值會變差，看到這行就去補那一格的樣板。
  在「設定 → 動作時間設定 → 手牌認不齊自救（秒）」可以調整，設 0 = 關掉自救、
  回到「認不齊就停著等你處理」。

- **比大小畫面一直 `比大小=—`**：這裡有三個已經修好的坑，列出來是因為它們
  被還原過一次（`test_highlow_corner.py` 守著，跑測試就會抓到）：

  1. `rightmost_card_rect()` 要回傳**量到的**牌寬牌高，不是校準框換算的
     `expected_*`（實機 160 對真實牌寬 149，差 11px 就足以讓右下角切歪）。
  2. `extract_parts()` 有收到 `rect` 時要以 rect 為準，不能讓 `expected_*` 蓋過去。
  3. 兩個角落**各自**的第一名一致時不再要求領先幅度 —— 那是兩次獨立取樣得到
     同一個結論，比「平均後領先多少」有力。這條**只開給比大小**：牌背是旋轉
     180 度對稱的，兩角必然一致，選牌畫面無條件開啟會把投注畫面的蓋牌讀成真牌
     （實測誤判 1/5 → 3/5）。

- **黑桃 / 梅花會搞混**：這兩個花色的角落小圖案最難分。解法是在「點數/花色樣板」
  分頁多存幾張**數字牌**（2~10、A），程式會一併存下卡面中央的大圖案，那個分得很開。
  同一個點數/花色最多留 8 張樣板，比對時取最高分。
- **常常認錯點數**：把視窗放大，並在「點數/花色樣板」分頁多存幾組。
- **點擊點錯位置**：確認長寬比沒有被改變（縮放沒問題，長寬比改變才有問題）；
  如果調整過遊戲解析度或長寬比，需要重新執行 `calibrate.py`。
- **滑鼠亂跑/誤觸**：把滑鼠移到螢幕任一角落即可透過 pyautogui 防呆機制強制停止，
  或按 F10 緊急停止。
